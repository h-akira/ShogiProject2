## なぜテストを導入するのか

### 現状の課題

現在、フロントエンド（`shogi-board`, `shogi-main`）にはテストランナーが導入されておらず、テストファイルも存在しない。開発中の動作確認はブラウザでの手動確認に依存している。

### テスト導入で得られるもの

| メリット | 説明 |
|---------|------|
| **リグレッション防止** | コード変更時に既存機能の破壊を検知できる |
| **リファクタリングの安全性** | テストがあれば、内部構造を変えても動作を保証できる |
| **仕様のドキュメント化** | テストコード自体が「この関数はこう動くべき」という仕様書になる |
| **開発速度の向上** | ブラウザでの手動確認を減らし、即座にフィードバックを得られる |

### 特にテストが有効な箇所

本プロジェクトでは以下の領域が特にテストの恩恵を受ける。

1. **将棋のゲームロジック** (`shogi-board/src/core/`)
   - 駒の移動・成り・持ち駒の計算など、複雑なルールを含む純粋関数群
   - バグがあると棋譜の再現が壊れるため、正確性が重要
2. **KIF/SFEN パーサー** (`kif.ts`, `sfen.ts`)
   - 入力文字列の解析は境界ケースが多く、手動テストでは漏れやすい
3. **API 連携を伴うページコンポーネント**
   - MSW によるモックが既に自動生成されており、テストに活用できる

## テスト戦略の全体像

### テストピラミッド

本プロジェクトでは「テストピラミッド」の考え方に基づき、下層から順にテストを充実させる。

```
        /\
       /  \         E2E テスト（将来検討）
      /    \        Playwright / Cypress でユーザーフロー全体を検証
     /------\
    /        \      コンポーネントテスト
   /          \     Vue コンポーネント単位で API 連携・画面遷移を検証
  /------------\
 /              \   ユニットテスト
/________________\  純粋関数・ユーティリティを関数単位で検証
```

| レイヤー | 対象 | ツール | 量 |
|---------|------|--------|-----|
| ユニットテスト | `core/` の純粋関数, `utils/` | Vitest | 多い |
| コンポーネントテスト | Vue ページ・コンポーネント | Vitest + Vue Test Utils + MSW | 中程度 |
| E2E テスト | ユーザーフロー全体 | (将来検討) | 少ない |

### 今回のスコープ

**ユニットテストとコンポーネントテストの環境構築と基本テスト作成**を行う。E2E テストは将来の課題とする。

## 対象パッケージ

### shogi-board（将棋盤ライブラリ）

`Frontend/shogi-board/` に配置。将棋のゲームロジックと盤面 UI コンポーネントを提供するライブラリ。

- `src/core/` — フレームワーク非依存の純粋関数（ゲームロジック、パーサー）
- `src/components/` — Vue コンポーネント（盤面、駒、再生コントロール等）
- `src/composables/` — Vue Composable（状態管理、再生制御）

### shogi-main（メインアプリケーション）

`Frontend/shogi-main/` に配置。ユーザーが操作する SPA 本体。

- `src/pages/` — 14 ページコンポーネント（棋譜一覧、作成、編集、タグ管理等）
- `src/components/` — 共通コンポーネント（ヘッダー、フッター）
- `src/utils/` — ユーティリティ関数
- `src/api/generated/` — Orval 自動生成の API クライアント + MSW モック
- `src/router/` — ルーティング定義（認証ガード含む）
- `src/auth/` — 認証モジュール

## ロードマップ

### Phase 1: 環境構築

- Vitest のインストールと設定
- テスト用の npm スクリプト追加
- MSW の Node.js 用セットアップ（`shogi-main`）

### Phase 2: shogi-board のユニットテスト

- `game.ts` — 局面操作（`applyMove`, `undoMove`, `replayToMove`）
- `sfen.ts` — SFEN の生成・パース（`toSfen`, `parseSfen`, `moveToUsi`, `parseUsiMove`）
- `kif.ts` — KIF の生成・パース（`toKif`, `parseKif`）
- `moves.ts`, `rules.ts` — 合法手生成・ルール判定

### Phase 3: shogi-main のユニットテスト

- `utils/explorer.ts` — `buildBreadcrumbs`
- `utils/labels.ts` — ラベル変換関数

### Phase 4: shogi-main のコンポーネントテスト

- 主要ページ（棋譜一覧、棋譜詳細、タグ一覧等）の表示・操作テスト
- MSW モックハンドラーを活用した API 連携テスト
- ルーターガードのテスト

### 将来の検討事項

- E2E テスト（Playwright）
- CI/CD パイプラインへのテスト統合
- カバレッジ計測と閾値設定
